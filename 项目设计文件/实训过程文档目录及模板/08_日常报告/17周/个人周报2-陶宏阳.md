## 二、详细工作内容

### 1. 简历解析重构

第一周提交的代码中简历解析使用了 BullMQ 队列异步处理，但 QueueService 未正确注册到模块中，导致空指针异常。本周完成了以下重构：

- **移除队列依赖**：去掉 `QueueModule` 导入和 `QueueService` 注入
- **改为同步解析**：`resume.service.ts` 直接调用 `resumeParser` 进行 LLM 解析
- **异常状态管理**：解析成功 → 更新 `parsed_data↵ + status=completed`；解析失败 → 更新 `status=failed` + 保存错误信息
- **try-catch 保护**：确保任何解析异常都不会导致接口崩溃，均有日志记录

### 2. 统一异常过滤器

实现 `AllExceptionsFilter`（91 行），替代原有的 `HttpExceptionFilter`，覆盖 6 类异常场景：

| 异常类型 | HTTP 状态码 | 处理逻辑 |
|:--------:|:----------:|----------|
| `HttpException` | 透传 | 保留原有 status 和中文 message |
| `Prisma P2002`（唯一约束） | 409 Conflict | 提取冲突字段名，返回可读提示 |
| `Prisma P2025`（记录不存在） | 404 Not Found | 提示"记录不存在" |
| `Prisma P2003`（外键约束） | 400 Bad Request | 提示关联数据不存在 |
| `PrismaClientValidationError` | 400 Bad Request | 参数格式错误 |
| `PrismaClientInitializationError` | 503 Service Unavailable | 数据库连接异常 |
| 未处理 Error | 500 Internal Error | 开发环境输出 stack trace，生产环境仅返回通用消息 |

所有异常统一日志格式：`[${method}] ${url} → ${status}: ${message}`

## 四、技术亮点与成果

### 亮点 1：AllExceptionsFilter — 6 类异常统一处理

```
Request → Controller → Service → Prisma/LLM
                                    ↓ 异常
                              AllExceptionsFilter
                                    ↓
                            ┌───────┴───────┐
                            │ 类型判断 + 状态码映射 │
                            └───────┬───────┘
                                    ↓
                   统一 JSON 响应: { statusCode, message, timestamp }
```

关键设计点：
- **Prisma 错误码映射**：`P2002`(唯一冲突)→409、`P2025`(不存在)→404、`P2003`(外键)→400
- **开发/生产模式**：`NODE_ENV=development` 时输出完整 stack trace，生产环境仅返回通用 message
- **统一日志**：所有异常均记录 `method + url + status + message`，便于链路追踪
- **验证失败优化**：class-validator 的数组消息自动提取第一条中文消息

### 亮点 2：简历解析去队列化

```
重构前: upload → Queue(未正确注册) → RESUME_PROCESS 事件 → 空指针 ❌
重构后: upload → LLM 解析(直接调用) → 状态更新(completed/failed) → 正常响应 ✅
```

- 移除了不必要的异步队列抽象，简化了数据流
- 添加了完整的异常状态管理（三种状态：pending/completed/failed）
- 保留了未来接入消息队列的扩展性（预留 Prisma 状态字段）

### 亮点 3：SDD 规范方法的应用

通过 SDD 规范分析，识别了项目中数据结构与操作分离的改进点：
- 异常处理从各 Controller 内聚到全局 Filter（关注点分离）
- 错误码从分散的魔法数字统一为状态码映射表

## 七、心得体会

**第二周的核心关键词是「提质」**。如果说第一周完成了从 0 到 1 的建设，那么第二周就是在为项目的长期健康运行打基础。

### 关于异常处理

AllExceptionsFilter 的实现让我对 NestJS 的异常处理体系有了全面认识。从最初的简单 try-catch，到后来分散在各 Controller 中的 HttpException 抛出，再到最终的全局统一拦截器，这是一个逐步完善的过程。设计异常过滤器时，**不仅需要考虑"能处理什么"**，还需要考虑**"不同环境该如何表现"**——开发环境需要完整的错误信息方便调试，生产环境则需要友好的错误提示保护敏感信息。

### 关于架构取舍

简历解析从队列异步改为同步解析，表面上看是一种"倒退"——移除了更复杂的架构。但实际上，**对于 MVP 阶段的项目来说，简单可靠的方案远比复杂完善的方案更有价值**。队列异步确实更优雅，但在团队人力有限、配置不完善的情况下，同步解析反而能提供更稳定的用户体验。

### 关于团队协作

本周通过代码评审和分支合并，我更全面地了解了团队成员的技术水平。前端同学在页面布局和交互上有不少亮点，但在代码规范和类型安全方面还需要加强。作为项目负责人，**下周的目标不仅是自己完成新模块开发，还要帮助团队成员提高代码质量**。
